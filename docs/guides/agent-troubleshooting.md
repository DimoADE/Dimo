# Agent 与协作部署：故障定位、恢复与验收

本指南用于区分 Host 管理授权、Agent 原生配置、模型服务、工具/联网搜索与协作部署故障，并给出可复用的诊断与恢复流程。相关架构契约见：

- 安装与认证分离：[ADR-0012](../adr/0012-agent-installation-and-authentication-are-separate.md)
- 原生配置权威：[ADR-0022](../adr/0022-agent-native-configuration-is-authoritative.md)
- 缺失能力诚实表达：[ADR-0058](../adr/0058-session-auxiliary-capability-honesty.md)
- 独立原生引擎优先、ACP 兼容次选：[ADR-0087](../adr/0087-dedicated-agent-engine-first-acp-fallback.md)

---

## 1. 分层定位：先确定失败发生在哪一层

| 层级 | 最小验证 | 不能由此推导的结论 |
| --- | --- | --- |
| Runtime | 实际执行路径、版本、启动或协议握手 | 版本命令成功不代表认证成功 |
| 认证与模型服务 | 用所选端点及其配套凭据完成一个可判分的小问题 | `/models` 或 HTTP 200 不代表有效回答 |
| Agent 工具 | 真实读取预置无敏感 canary 文件，并使用返回内容回答 | 模型自述或发现工具目录不代表执行工具 |
| 搜索与抓取 | 检查实际搜索事件、来源、页面打开或抓取结果 | 写出 URL、`search_tool` 发现工具不代表联网搜索；搜索成功不代表独立抓取成功 |
| Host 管理 | `list_spaces({})`、`manage_bot({"action":"list_agents"})` | 模型 API 成功不代表管理 MCP 可用 |
| 协作部署 | 实际主管身份、创建结果、真实 ID 回读、成员及任务回执 | 角色草稿、普通 Conversation 或模型测试通过不代表 Bot/群已部署 |

诊断纪律：

- 每项记录测试时间、Host/工作区归属、Agent 运行路径与版本、配置来源、请求与响应模型 ID、结果、耗时与证据类型；第三方渠道的模型标识不是底层权重的独立认证。
- 状态严格区分为 **通过 / 失败 / 不支持 / 未测**；单层通过不得替其他层标绿。
- 在授权范围内使用小预算、明确超时的测试：先分别验证回答、文件工具和联网搜索，再验证组合任务；保留先失败后通过的记录，不以单次冒烟承诺长期稳定。

## 2. 管理 MCP 返回 `user rejected MCP tool call`

按以下顺序排查，避免盲目重试或误判根因：

1. **收敛为只读验证**：先调用 `list_spaces({})` 与 `manage_bot({"action":"list_agents"})`，记录原始返回与时间戳，立即停止无变化的重复批量创建。
2. **关联协议事件与界面审批卡**：将同一请求的 Agent 授权事件、Host 权限事件与界面权限卡一一对应。客户端日志中的 `ResolveElicitation ... decision: Decline` 仅证明收到了拒绝决定，不能单独推导为用户手动点击拒绝；聊天文本里的业务授权与宿主权限卡的协议回传属于不同层面。
3. **核对 Host、Binding 与数据目录归属**：确认当前 Conversation 归属的 Host 实例、Agent binding 代次与 SQLite 数据目录。在某一数据库未查到记录，不能直接断定会话丢失或缺少主管权限，可能指向了另一个 Host 或数据目录。
4. **保留脱敏协议证据**：若底层协议或引擎驱动不支持某类服务端请求（如未实现的 elicitation RPC 方法返回 `-32601`），保留方法名、协议版本、错误码与回传路径的脱敏证据；不以自由文本臆断根因，也不得通过关闭全局审批或手工改写内部数据库绕过拒绝。
5. **核实主管身份与协作入口**：读取恢复后再确认实际主管身份——将普通 Bot 命名为“主管”不会赋予主管权限。界面中协作空间列表的 **＋ → 创建群聊 / 创建助手** 与联系人分类 **新建分组** 属于不同操作。
6. **区分原生引擎与 ACP 通道**：排查协议行为时先确认当前会话命中 `EngineRegistry` 的独立原生引擎还是 ACP 兼容通道（见 [ADR-0087](../adr/0087-dedicated-agent-engine-first-acp-fallback.md)）。使用产品支持的会话重连、重绑定或切换引擎诊断时，应先明确会话语义并重新运行只读验收；不要假设重启或升级必然解决授权问题。

## 3. OpenCode / DeepSeek 认证与渠道恢复

遇到 `provider.auth` 或 HTTP `401` 时，先定位 OpenCode provider options、原生认证文件与环境变量中的凭据来源及端点归属。诊断输出只记录来源名、是否存在及匹配结果，绝不打印凭据值或完整命令参数，也不要在不同渠道间交叉试投密钥。

恢复步骤：

1. **先备份原生文件**：私下备份即将修改的原生配置与认证文件并记录回滚路径；备份含密钥，不得作为报障附件。
2. **独立验证端点与有效回答**：核对渠道目录及实际可用模型，用该端点配套的有效凭据发送一个可判分的最小问题（例如简单算术）；返回无关内容（如 `pong`）即使 HTTP 200 也不算通过。
3. **同步配置与模型映射**：端点验证通过后再同步 `base_url`、认证与显式模型映射，并核对默认模型与轻量任务模型。切换至可用渠道属于配置恢复，不代表原故障供应商已修复。
4. **分层复测新会话**：新建会话先验证纯文本回答，再验证 Agent 真实读取预置 canary 文件并依据文件内容作答；直接 API 成功不等同于 OpenCode 或 Dimo Bot 完整可用。
5. **确认配置生效与隔离影响**：保留超时等失败记录，核实后台服务或常驻进程是否已加载新配置；切勿为单次诊断中断用户其他正在运行的任务。

## 4. Grok 自定义渠道：回答、模型选择与联网搜索

Grok 原生配置中，本地 `[model.<table>]` 的表名与发给上游的 `model` 字段不是同一概念：`models.default` 与 CLI 选择值须解析到包含正确端点与凭据的表，不应将显式 API 模型 ID 未经验证地视作自定义表别名。

仅在目标渠道确认支持后端搜索时，按当前安装 CLI 的文档为对应自定义表补充搜索能力声明（以下为字段增补示意，请保留原有 `model`、`base_url`、认证与 `api_backend`）：

```toml
[model.<custom_table>]
# 保留现有 model、base_url、认证与 api_backend。
supports_backend_search = true

[models]
# 保留其他已有选项。
web_search = "<custom_table>"
```

排查与验证要点：

- **勿对所有 OpenAI-compatible 渠道默认开启后端搜索**；开启前先在该渠道实测。
- **按序分层验证**：自定义表回答 → 文件读取 → 真实搜索 → 显式模型选择 → 在隔离配置中经设置页保存供应商 → 新会话复测。
- **核对端到端搜索证据**：服务端 `web_search_call`、客户端工具事件与最终引用须相互对应；独立 `web_fetch` 不可用时单独标记状态，不得因搜索通过而一并标绿。
- **分离上游异常与配置问题**：遇到 `503`、流式重试或托管目录告警时，分别定位上游服务、协议与配置来源；诊断时可临时限制重试次数，但降低重试不会修复上游故障。
- **保存回写回归核查**：若在 Dimo 设置页保存供应商后自定义扩展字段被覆盖，应在隔离配置中对比保存前后差异，依据 [ADR-0022](../adr/0022-agent-native-configuration-is-authoritative.md) 核查字段保留策略，勿在生产配置直接盲测。

## 5. 上游服务与外部环境故障隔离

在将异常归因于 Dimo Host 或引擎驱动之前，先在宿主机原生 CLI 或独立网络环境中做最小对照复测：

- **抓取/安全校验失败**（如原生 CLI `WebFetch` 报目标域名安全检查失败）：在沙箱外独立复测，以区分宿主沙箱策略与上游工具/策略限制。
- **第三方兼容端点报错**（如兼容 `/responses` 或搜索参数返回 HTTP `400` / `404`）：分别测试纯回答、受控工具调用与搜索参数，避免将网关能力差异误判为模型原生能力缺失或驱动缺陷。
- **更新检查与网络错误**：独立验证网络与代理路径，将瞬态网络故障与客户端代码缺陷分开记录。
- **跨平台命令包装问题**：在 Windows 排查多行 prompt 时，优先直接调用原生可执行文件而非 `.cmd` 包装脚本，避免脚本转义失真干扰归因。

## 6. 回滚纪律与验收清单

### 回滚纪律

- 修改任何 Agent 原生配置文件前先保留同版本备份；回滚时成对恢复配置与认证文件，并在新会话中重新验证。
- 不要在 Dimo 设置页保存与手工编辑之间并发修改同一原生文件。
- 不要把重启正在运行中的会话当作默认排障步骤；新会话与既有会话的绑定语义须分别核实。

### 完整验收清单

- [ ] Host 只读管理调用成功，权限卡与协议回传一一对应，实际主管身份已核实。
- [ ] 单一 Bot 与单一群组完成创建、真实 ID 回读、模型绑定与成员验证后，再扩展部署。
- [ ] 任务具备真实派发与投递回执；定时或事件协作具备实际落地的调度/规则配置。
- [ ] 自定义渠道在保存供应商配置后仍保持预期能力；不支持搜索或抓取的渠道诚实呈现能力缺失。
- [ ] 原生 API、Agent CLI、Bot 协作与 Host 管理分别独立验收，未测项保持“未测”。

### 脱敏报障规范

向 [官方 Issues](https://github.com/DimoADE/Dimo/issues) 提交前先检索去重，明确区分**已证实根因、推测、修复动作、实测结果与未完成项**。仅附最小脱敏证据：禁止上传完整配置文件、令牌、数据库、原始聊天记录、模型内部推理或业务资料；命令行参数数组与环境变量同样可能包含密钥，须整体检查脱敏而非仅按 JSON 键名过滤。
